# Contract 与 Writer 协议

本协议规定观点契约分析者与 Writer 两个角色。它只约束这两个角色，不增加 Reviewer、局部编辑者、`PASS／FAIL`或修复循环。

“独立”是指不共享前一角色的对话历史、草稿推理和自我评价的新上下文。可以使用同一模型，但必须是新会话、子任务或宿主提供的隔离执行单元。在原上下文里换一个角色名、声称“冷读”或再读一遍，不算独立。

## 知识稿的六条写作要求

这六条是两个角色共同的目标。契约负责让它们有材料可写，Writer 负责把它们写出来。与本协议及知识校验其他条款冲突时，以这六条为准；但不得因此违背“不变原则”中的知识归属和非虚构要求。

1. **有推导，读完能说出“通过这件事看清了什么”。** 文章要从用户的经历推出一个读者原先没想到的判断。用户已经在原话或附件里写明的结论，只能当作起点或证据；契约要找出材料支持的、更进一步的一层。每一步连接都必须能回指`01`，找不到时如实停在用户已有的结论，不编造。更进一步的这一层是文章对材料的推论，正文用“这说明……”一类文章层面的说法写出，不写成用户当时已经想到的原话或经历。提出这一层后，逐个对照文中用到的案例检查有没有反例；有反例时收窄判断的范围，不忽略反例。推论不能当作已知事实，再拿去支撑别的判断。
2. **站在读者角度。** 用户的经历是回答读者问题的例子。文章回答读者关心的问题，让读者看到自己的困惑被解答，不写成只讲作者自己的故事。
3. **用户原话清楚、有力时用原话。** 原话啰嗦时才精炼。不把用户已经说得好的句子换成意思相同但更平淡的 AI 表述。文章以作者第一人称叙述时，作者自己的原话直接写进句子，不加引号，也不先转述一遍再引一遍；别人说的话才用引号。口语原话可以整理断句和标点，不改用词。
4. **不反复限定。** 事实边界只在会被误读成更大结论的地方处理一次，用准确的主语、限定词或“我觉得”“可能”写进句子本身。不在段尾、文末重复“只能说明……”“不能据此推断……”。
5. **删掉不服务主线的内容，保留的内容也要判断留几句。** 能用一句说清的例子不写一段。删去后读者不会少懂什么的句子，删。Writer 据此压缩句子，不删除契约已定为保留的条目。
6. **逻辑上重要的内容不能删。** 判断标准见下文“重要性闸门”。

## A. 观点契约分析者

输入只有`01`、`02`头部的阶段状态（若有）和用户当次明确要求。阶段状态只作索引，用来定位主 QUD、已确认结论和暂留项在`01`的哪些轮次；与`01`不一致时以`01`为准，标为“待确认”的采访者概括不得当作用户已确认结论。不得读取旧`02`正文、候选稿、后续阶段产物或历史编辑清单。

### 只选一个主问题

一份知识稿只回答一个主 QUD。采访中有两个以上都能独立成文的问题时（各自有足够材料回答，且回答不依赖另一个问题），契约只选一个作为主 QUD：优先选用户在采访中明确说“我想聊的是……”的问题，用户前后说法不同时选后说的；没有明确说法时，选材料最完整的。其他问题整体转为独立旁支，由主 Agent 在成稿后放进“可独立展开的选题”或“待探索的素材”，不在正文里压缩着讲。未入选问题里只有为主 QUD 提供必要证据的那一部分可以进正文，按证据的最小量写。

### 契约输出

输出一份临时观点契约，至少包含：

- 主 QUD；解释型问题同时包含`P–X–R`；转为旁支的其他独立问题，各写一句；
- 读者原有困惑、本文应给出的新判断和可感知用途；新判断须写明它比用户已有原话多推进了哪一步，以及这一步依据哪些轮次（见六条要求第 1 条）；材料不支持更进一步时写“无，停在 T00X 的用户结论”，这是正常结果，不算失败；
- 每个候选判断的编号、主体、对象、方向、强度、成立条件、材料位置、对主 QUD 的作用，以及后续材料对它的 `support`／`qualify`／`revise`／`refute` 关系、`核心结论／必要推进／可选支撑／内部边界／独立旁支`正文责任、展开深度和保留／合并／排除理由；
- 证据选择：同一判断有多个案例时，只合并含义相同的案例，选最接近用户原话、信息最完整者写出，其余合并成一句概括。案例之间理由、机制或含义不同时，分别保留，各用最短篇幅写。不得编造数字，也不得把“有人”写成“所有人”；
- 已排好顺序的观点主线。解释型主 QUD 使用`最反常的事实 → 被推翻的默认判断 → 最先说出的反预期结论 → 必要证据与解释 → 仍未解决的矛盾 → 更深一层判断`；只有回答上一层残余矛盾的判断才进入下一层。材料没有反预期关系时按真实的时间、条件、因果或判断依赖排序，不强造反转；
- 说话人与人称映射；
- 观点归属映射：区分用户明确表达的判断与 Agent 推导；用户对具体当事人心理、动机、需求或关系的判断仍属于用户知识，按原强度写：不因当事人未亲口确认而降调，也不升调；
- 材料角色：主线证据、必要支撑、必要边界、背景或旁支；
- 能回指`01`并由正文兑现的开头亮点候选；
- 建议保留的用户原话：从`01`中选出最清楚、最有力、能承担主线判断或关键证据的原句，最多 8 句，每句标轮次和它对应的主线节点。它是表达优先项，Writer 可以截取或调整语序，不必全部用上；
- 内部取舍记录：只记录有`01`轮次、值得交代去向且被压缩或排除的候选材料；每条一行，格式为“删了什么（`01`轮次）｜为什么删｜现在在哪”。“为什么删”用一句平常话写，依据下面的五条标准；“现在在哪”写“并入正文：……”“转出”或“只留在 01”，由主 Agent 扫描时决定归入选题还是待探索。证据不足一类只记录可进入待探索的用户线索，不记录没有来源的 Agent 推测。按“只选一个主问题”转出的问题写“转出”，其中为主 QUD 提供证据的部分写“并入正文：……；其余转出”，不能写“只留在 01”。此记录不是逐句台账，成稿后由主 Agent 原样转入`02`末尾的“取舍说明”，不得事后另编理由。

### 取舍标准与重要性闸门

删减或合并时，理由只能是以下五条之一：

- **非必要**：删去后主 QUD 的答案仍成立，读者的主要疑问仍能回答。
- **同类重复**：已有含义相同、且更强或更完整的证据，合并为一句。含义不同的不算重复。
- **用户已标为旁支、背景或留到以后**，或属于“只选一个主问题”中转出的其他问题。
- **附带收益**：不改变、不支撑、不限定主 QUD 的答案。
- **证据不足**：材料不能支撑成句，只是推测。

重要性闸门：以下服务主 QUD、且有`01`材料支持的材料，不得以“非必要”“同类重复”“附带收益”删除或写弱，只能决定写多长（“证据不足”和“旁支／转出问题”两条照常适用）：

- 核心结论与必要推进；
- 能单独改变读者对现象的解释的判断或案例，即使它和别的案例话题相近；
- 用户自己点明的新发现、命名或比喻（例如用户明确说某个看法是自己新想到的，或用户自己给出的概括性说法）；
- 删去后，推导链中某一步会失去依据的材料。

拿不准是否触发闸门时，保留并压缩成一句。

### 契约边界

契约不写作正文，不推荐理论；契约本体不进入`01`或`02`，仅取舍说明按主文件格式进入`02`。除“建议保留的用户原话”外，不得把契约扩张成逐句保留台账或原句锚点清单；只有服务主 QUD 的核心结论与必要推进进入观点主线。

契约中的 `qualify`、事实边界和“不推广”等记录，用于控制正文判断的强度。只对带 `qualify` 或事实边界、且会被误读成更大结论的核心结论，契约写明正文应使用的强度措辞（例如“我觉得”“可能”）；其余写“按原强度”。用户原话是确定语气时不得加“可能”；用户原话带“可能”“我觉得”时，正文保留，不去掉。Agent 推论的强度不得高于它最弱的前提。契约不另写需要 Writer 照抄的免责句。

## B. Writer

输入为`01＋观点契约（含观点主线）`及主文件的写作规则。不得读取候选理论、旧稿或后续审核结论。Writer 严格沿观点主线成稿，不重新选择中心或顺序。

写作时先满足本协议开头的六条要求。具体做法：

- 正文在最少必要情境后先写本层判断，再写证据和解释；只有判断已给出且材料仍有真实缺口时，才用问句开启下一层；
- 契约列出的“建议保留的用户原话”，在对应位置优先使用；
- 契约里的边界和 `qualify` 只用来决定句子强度，不写成单独的免责句；同一边界对同一判断最多出现一次；
- 并列理由如实成组，不制造递进；不写元标签和防御性回拽；
- 案例细节只写`01`里明确出现的主体、动作和先后；`01`没有说清的细节，不写或照原话写，不替它补全；
- 正文默认不用小标题，写成一篇连续的文章；用户要求分节时才加；
- 最后一段把全文的推导收成一个判断，回答开头提出的问题，不另起新论点，也不在收束后再补一段。
- 全文最强的结论在推导完成后才说出。前文可以提出问题，但不提前说出这个结论；契约指定给结尾节点的原话，前文不使用；
- 用户标为背景、旁支或留到以后的材料，正文不写，契约明确列为必要证据的除外；
- 结尾不加材料里没有的建议、行动号召或评价。
- 开头和过渡不虚构材料里没有的争论或说法（例如“有人说……也有人说……”）；需要对比时，用`01`里实际出现的对比；
- 转述对话或聊天记录时，只留推进当前判断所需的一两句，其余用一句概括；不整段照搬口语转录。
- 数字、人数和金额照`01`原话写，不自行相加、换算或改变它们对应的范围。

输出只包含不带理论的基线稿。

Writer 可自查，但自查不得反向扩张观点契约、恢复已排除材料，或把审计边界写进正文。自查时逐条对照六条要求，发现问题在当前写作中直接改正。

## 运行边界

两个角色必须先后运行，不得合并或并行。观点契约返回后才启动 Writer。某个角色启动后失败或返回空结果时，只重启该角色一次。宿主无法创建隔离上下文、或重启后仍失败时，按主文件“子智能体不可用时”处理，不得在主 Agent 当前上下文里串行扮演两个角色。
