# QWS 升维

## 作用

帮用户跳出在局部反复打转的状态：检查问题、目标和默认前提是否成立，选择保留原框架、扩大系统范围或重新定义问题，并在同一条回复里给出改法或需要用户决定的那一项。整篇文案、整套方案、代码和发布等完整业务产物，仍交回原任务。

已发生的执行失败归因（例如格式没保存对、命令执行出错）不在本 Skill 范围，留在当前任务处理。

## 需要读取的文件

- 深度升维前，完整读取 `references/system-scope-model.md`。缺失时说明缺少该文件，只做轻量检查，不编造层级或步骤。
- 深度升维时再按任务类型读取落地文件：修改文字（句子、段落、指代、措辞）读 `references/landing-text.md`；内容与账号相关（视频、选题、框架、标题封面、加粗重点、账号定位、阶段、议程）读 `references/landing-content.md`；其他任务不读。落地文件只提供落地方法，不改变本文件的流程。

## 原则

1. **原框架也要过事实检查。** 用户和 Agent 的问题定义都要核实；成立就保留，不为升维而升维。
2. **分清诉求、目标、指标和手段。** 可以质疑目标，但价值取舍由用户决定。
3. **改框架要有交代。** 说明改变了哪项解释、目标、原因、方案、风险、责任层或验收标准，以及依据。
4. **分析范围 ≠ 执行范围。** 发现问题在上层时，退回最早受影响的环节，不把整个系统的责任压给眼前对象。
5. **新答案必须比 A 好才采用。** 对照检查前仍成立的答案 A，看新答案是否更准确地解释事实或推进原诉求；层级更高、听起来更深刻都不算理由。没有净改善就保留 A；A 已被事实推翻时重新校准，不能借回退保留错误。

## 流程

### 触发

- **深度升维**：用户明确要求时进行。用户只说「升维」两个字就够了；说「升维 Skill」「从全局看」「这是不是局部问题」「检查是否只在局部解决」，或直接调用 `/qws-zoom-out`，都算明确要求。
- **提示升维**：用户没有明确要求，但对话显示他在同一件事上反复修改仍不满意时，只在当前回复末尾加一句提示，不自动展开升维分析，原任务照常完成。按意思判断，不只匹配固定句子。常见的意思包括：
  - 对同一处修改连续表示不满意：「还是不对」「不是这个意思」「感觉哪里不对，但说不上来」「都不太行」「再换一个」；
  - 越改越差或想退回：「越改越差」「还不如原来的」「算了，还是用第一版吧」；
  - 觉得 AI 的判断在摇摆：「你怎么一直在变」「刚才不是这么说的」「又改回去了」；
  - 不同来源给出的方向冲突，用户拿不定主意：「几个 AI 说的都不一样」「我也不知道该听谁的」；
  - 同一个问题修好又出现，或规则、补丁越加越多却不见效。
  提示句为：「这个问题可能卡在局部了。需要的话说『升维』，我从更高的维度帮你看一下。」以下情况不提示：用户第一次提修改意见；用户给出明确、具体的修改指令（例如“把这个词换成某某”）；问题是执行错误，例如文件没保存对、命令执行失败。同一件事只提示一次；用户没有回应时不再重复，除非之后又出现新一轮反复修改。
- 措辞里出现「战略」「架构」等词，但实际只是局部小改时，不构成升维理由。

### 轻量检查

依次问：用户要理解或改变什么，预设了哪些目标和因果；哪些事实支持或反驳这些预设；缺的是系统关系还是问题定义有误。结论归入四类：

| 结果 | 动作 |
|---|---|
| 局部足够 | 留一行可见痕迹，例如「轻量边界检查：原框架成立，直接返回」，带着问题定义返回原任务 |
| 局部处理＋上层约束 | 写明约束再返回 |
| 上移责任层 | 先处理上层，再回到局部 |
| 边界尚不能确定 | 先按最可能的情况给出判断并写明假设，再只追问最关键的一项 |

### 深度升维

先做第 0 步，再按 `references/system-scope-model.md` 完成第 1–4 步。

0. **锁定 A 和打转记录。** 明确写出答案 A：用户明确认可过的版本；没有时，用打转开始前的那一版（最早的原稿，或已经发布、正在使用的版本）。A 不是最后一个被否定的版本；后来的讨论批评过 A，不等于 A 被推翻，只有用户明确否定或新事实推翻才失效。所有候选都与 A 比较，在 A 上微调也算有效答案。再找出已试方案共享的前提或共同的改动位置，并对照 reference 中的「常见打转成因」认出这是哪一类打转；表里没有对应类型时，也要自己判断并说出是哪一种。
1. 校准问题与目标。
2. 选择路径：扩大边界、换框架，或两者结合。扩大边界时在本次完成有依据的父级链检查；换框架时比较问题定义，不强行套成「更高一层」。
3. 对照 A 比较候选。采用新方案时，它必须换掉第 0 步找到的共同前提；只换措辞的候选仍在原地打转。
4. 返回原问题，确定停止边界，给出改法。

要求：

- **一次调用给出最终结果。** 往上查到「再上一层就会改变原命题、原问题，或用户已确定的定位、目标、价值取舍」为止；更上一层只写成约束或待用户决定的事项。
- **交付前自检。** 假设用户马上再调用一次：往上一层或换个框架会不会得出不同答案？会且不改变原命题，就本次继续检查；否则停下交付。同时确认答案回答了最初的疑问，而不只是在新框架里看起来正确。
- **防空转。** 深度检查后若没有改变任何解释、目标、原因、方案、风险、责任层或验收，改判为「局部足够」，用一行痕迹返回；因用户要求而检查的，注明「已按你的要求检查：原框架成立」。
- 完成后在当前任务里保留精简的 `Active Scope State`（见下），不展示给用户，除非用户要求。

## Active Scope State

必填 5 项，其余只在用到时填写；不涉及的写「不涉及」，不虚构层级。只留在当前任务和 Agent 日志中，不写入用户文稿或长期档案。

```markdown
## Active Scope State
- 用户真正要推进的结果：
- 边界与选择依据（保留／扩展／重定义）：
- 应该介入的层级：
- 原任务必须继承的约束：
- 停止边界及原因：
- （按需）原因判断、关键关系、验收标准、未知与失效条件：
```

## 连续性

- 再次调用时先继承已有状态；没有新事实就沿用原边界和答案，不因用户说「再升一次」制造新答案。
- 新事实或复核改变了问题定义、目标、原因、方案、风险、责任层或验收时，重新检查；复核发现旧判断有误，要指出漏掉的事实，不用「没有新材料」锁住错误。
- 后续执行继承该状态，不把系统性问题静默降回局部问题。

## 交回原任务

- 判断和改法在同一条回复里给出，不等用户再问「怎么办」：
  - **小改动**（一句话、一处指代、一个标题、一处加粗、一个参数）：给 1–2 个候选；
  - **大改动**（换目标、换定位、换框架、改变价值取舍）：给判断和可选方向，只问一个决定后续路径的问题，用户选定后再给具体改法；
  - 用户明确只要诊断时，只给判断。
- **改法只动定位到的那一处。**顺带发现的其他问题，用一句话列为「可选」，不写进改法，也不建议删段、改写其他句子或重写整篇；用户已定稿或明确要保留的内容不动。改法要保留用户原来的判断：只解决定位到的问题，不替换用户的结论、立场或评价标准，也不改变原句的语气强度。
- 需要局部动作时附**落地规格**：改哪里、要完成什么、不能破坏什么、怎么验收。
- 缺少事实时，先从用户的文件和对话里找；找不到就按最可能的情况给出判断和改法并写明假设，问题放在末尾，只问一个，尽量给可选项。
- 价值取舍由用户决定；不路由到其他具名 Skill。

## 正反例

- **该升维**：「从全局看：转化率掉了，帮我改落地页文案。」同期流量来源、定价、客服话术都改过，「转化」口径还混了试用和付费。→ 重新定义问题，先校准指标和原因，再交回文案任务。
- **局部足够**：「把这段说明里的错别字改掉。」→ 一行痕迹，直接返回。
- **没喊只提示**：用户第三次说「还是不对」，但没有要求升维。→ 照常完成这次修改，在回复末尾加一句「这个问题可能卡在局部了。需要的话说『升维』，我从更高的维度帮你看一下」，不展开分析。
- **假升维**：改一个函数名，却产出完整父级链和状态表，没有改变任何判断。→ 改判局部足够。

## 用户可见输出

默认只说四点：

1. 卡在哪：写出打转类型的名称和最关键的一条依据，并且必须写出下面二者之一：这类问题的成熟做法名称；没把握时，至少两个可以搜索的关键词。
2. 保留 A 还是换成 B；换成 B 时说出 B 在哪条具体事实或诉求上更好。
3. 改法：小改动给候选，落地规格压缩成一两句跟在后面；大改动给可选方向并只问一项。
4. 停在哪：一句话说明再往上会改变什么，以及剩下的那个需要你决定的问题。

写法要求：

- 打转过程用一句话概括，不逐条复述试过的版本；每个判断只给最关键的一条依据。
- 小改动的回复控制在 600 字左右，大改动在 1200 字左右；超出时先删解释，不删改法和候选。
- 不展示 `Active Scope State`、理论来源或内部检查过程，用户要求时再展开。
